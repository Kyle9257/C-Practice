## 前置：先搞懂一个词 —— target（目标）

CMake 里一切围绕 **target** 转。一个 target 就是「要产出一样东西」的声明：

- `add_library(...)` → 产出静态库/动态库（`.a` / `.lib` / `.dll`）
- `add_executable(...)` → 产出可执行程序（`.exe`）

每个 target 回答三件事，这就是验收清单里反复出现的「target 三要素」：

| 要素 | CMake 命令 | 问题 |
|---|---|---|
| 它是什么 | `add_library` / `add_executable` | 要产出啥？ |
| 它暴露什么 | `target_include_directories(... PUBLIC)` | 别人用我时能拿到什么（头文件在哪）？ |
| 它依赖什么 | `target_link_libraries(...)` | 我需要链接谁？ |

先记住这个框架，后面每一步都在验证它。

## 第 14 项 · CMake —— 跟着走一遍

### 第 1 步：先理解项目的「物理分层」

打开 `exercises/cmake_demo/`，它有四个目录 + 四个 `CMakeLists.txt`：

```
cmake_demo/
├── CMakeLists.txt        ← 顶层：定项目、定标准、声明子目录
├── src/                  ← 库代码（vec3.h / vec3.cpp）
│   └── CMakeLists.txt    ← 建静态库 vec3
├── app/                  ← 入口程序（main.cpp）
│   └── CMakeLists.txt    ← 建可执行 demo，链接 vec3
└── tests/                ← 测试（test_vec3.cpp）
    └── CMakeLists.txt    ← 建测试程序，链接 vec3，注册给 ctest
```

**为什么要分层？** 把「可复用的库」和「用库的程序」分开，是真实工程的最小模型。你的 `TransFormCore` 坐标变换库，未来就该像 `src/` 里的 `vec3` 这样被 `app` 和 `tests` 共用。

### 第 2 步：逐层读 CMakeLists，对照三要素

**顶层 `CMakeLists.txt`**（项目的大脑，不产出东西，只做全局设定）：

```cmake
cmake_minimum_required(VERSION 3.15)   # 最低 CMake 版本
project(TransFormCoreDemo CXX)          # 项目名 + 语言 C++

set(CMAKE_CXX_STANDARD 17)              # 用 C++17
set(CMAKE_CXX_STANDARD_REQUIRED ON)     # 编译器不支持就报错，不降级

enable_testing()                         # 开启 ctest 能力（第 15 项会用到）

add_subdirectory(src)                    # 往下钻三个子目录
add_subdirectory(app)
add_subdirectory(tests)
```

**`src/CMakeLists.txt`**（第一个真正产出东西的 target —— 静态库）：

```cmake
add_library(vec3 STATIC vec3.cpp)       # 是什么：静态库 vec3
target_include_directories(vec3         # 暴露什么：头文件目录 PUBLIC 给所有依赖者
    PUBLIC ${CMAKE_CURRENT_SOURCE_DIR})
```

- `STATIC` = 静态库，编译进最终程序里，不需要额外 dll。
- `PUBLIC`：谁链接了 `vec3`，谁就自动拿到这个 include 路径 —— 所以 `app` 和 `tests` 里才能直接 `#include "vec3.h"`，不用自己写 `-I`。

**`app/CMakeLists.txt`**（可执行程序）：

```cmake
add_executable(demo main.cpp)            # 是什么：可执行 demo
target_link_libraries(demo PRIVATE vec3) # 依赖什么：链接 vec3
```

- `PRIVATE`：只有 `demo` 自己需要 `vec3`，不会往外传。

**`tests/CMakeLists.txt`**（测试程序 + 注册给 ctest）：

```cmake
add_executable(test_vec3 test_vec3.cpp)
target_link_libraries(test_vec3 PRIVATE vec3)
add_test(NAME vec3_tests COMMAND test_vec3)   # 注册给 ctest，名字 vec3_tests
```

### 第 3 步：动手跑「配置 → 构建 → 运行 → 测试」四连

> ⚠️ 本机系统默认 `cmake` 是 4.2.0-rc2（RC 版有崩溃 bug）。统一用稳定版 `C:\Strawberry\c\bin\cmake.exe`。

```bash
CM=/c/Strawberry/c/bin/cmake
cd tier4_toolchain/exercises/cmake_demo

"$CM" -B build -G Ninja            # ① 配置：生成 build/ 里的构建文件
"$CM" --build build                # ② 构建：编译出 demo.exe / test_vec3.exe
./build/app/demo.exe               # ③ 运行程序
"$CM" --build build --target test  # ④ 跑测试（等价 ctest --test-dir build）
```

**四步各自在干嘛？**
- **配置**：CMake 读 CMakeLists，算出「要编译哪些文件、用什么编译器、什么选项」，写进 `build/`。这一步**不编译代码**。
- **构建**：真正调用编译器（g++），产出 exe。
- **运行**：执行程序看结果。
- **测试**：跑注册过的测试 target，报通过/失败。

### 第 4 步：PUBLIC vs PRIVATE —— 用实验理解

这是验收清单里最难记清的一条。做一个思想实验：

把 `app/CMakeLists.txt` 里的 `PRIVATE` 改成 `PUBLIC`，再运行，**行为完全一样**。那区别在哪？

- 区别只对「依赖 demo 的人」有意义。现在没人依赖 demo，所以没差别。
- 换成 `vec3` 就明显了：`vec3` 的头文件目录是 `PUBLIC`，所以 `demo`、`test_vec3` 链接 `vec3` 后**自动**能 include `vec3.h`。
- 如果 `vec3` 的 include 是 `PRIVATE`，那 `demo` 编译时就会报「找不到 vec3.h」——因为 include 路径不外传。

**一句话记法**：`PUBLIC` = 我的依赖者也要用；`PRIVATE` = 只有我自己用；`INTERFACE` = 我自己不用、只给依赖者用（纯头文件库常见）。

## 第 15 项 · GoogleTest —— 用专业框架替代手写断言

### 为什么需要 gtest？

看 `tests/test_vec3.cpp`，它用**手写断言**（`expect_near` + 全局 `failures` 计数）验证结果。能用，但有两个问题：

1. 每个测试都要自己写 `if (失败) 打印 + 计数 + return 1`，重复且容易漏。
2. 失败时信息少，看不出是哪个用例、期望什么、实际多少。

gtest 用 `TEST` 宏 + `EXPECT_EQ` 帮你把这一切标准化，还自动生成 `main` 函数、自动统计、自动输出漂亮的失败报告。

### 第 1 步：读 gtest 版的测试

`exercises/gtest_demo/test_calc.cpp`：

```cpp
#include <gtest/gtest.h>

int add(int a, int b) { return a + b; }

TEST(CalcTest, Add) {              // TEST(套件名, 用例名)
    EXPECT_EQ(add(2, 3), 5);       // 断言：实际 == 期望
    EXPECT_EQ(add(-1, 1), 0);
    EXPECT_EQ(add(0, 0), 0);
}
```

三个关键点：
- `TEST(套件, 用例)`：定义一个测试用例。同「套件」的用例归为一组。
- `EXPECT_EQ(a, b)`：断言 a 等于 b。**失败不中断**，继续跑完当前用例。
- `gtest_main`（见 CMakeLists）：gtest 提供的库，帮你生成 `main` 函数，不用自己写 `int main`。

### 第 2 步：理解 FetchContent —— 怎么把第三方库拉进来

`exercises/gtest_demo/CMakeLists.txt`：

```cmake
include(FetchContent)
FetchContent_Declare(
    googletest
    GIT_REPOSITORY https://github.com/google/googletest.git
    GIT_TAG v1.14.0
)
FetchContent_MakeAvailable(googletest)   # 首次配置时自动 git clone + 编译

enable_testing()
add_executable(test_calc test_calc.cpp)
target_link_libraries(test_calc PRIVATE gtest gtest_main)
add_test(NAME calc_tests COMMAND test_calc)
```

`FetchContent` 是 CMake 3.11+ 的官方机制：**在配置阶段**自动下载第三方源码并一起编译，不用你手动装库。这是现代 CMake 管理依赖的主流方式。

## 两个主题的关系（一句话）

**CMake 负责「怎么构建」，gtest 负责「怎么验证构建出来的东西对不对」**。真实项目里，CMake 把 gtest 作为测试 target 接入（`add_test` + `enable_testing`），`cmake --build --target test` 一条命令跑完所有测试。
